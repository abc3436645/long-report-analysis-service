# 财务公司授信风险评估与审查：场景规格

版本：业务规格v0.5｜日期：2026-10-21｜状态：C01—C04及Q42—Q51已确认，Q49补充在建项目；2026-10-27补充真实样本固定结构与字体配置；具体政策、材料字段、实际来源接入及业务验收仍待验证。

依据：[主框架](../通用长报告项目-统一架构与业务流程.md)、[决策记录](../架构细化-决策树与访谈记录.md)、[术语表](../../GLOSSARY.md)。本规格修正原先“对财务公司自身尽调”的理解，不表示已有运行能力。

## 1. 已确认的业务含义

用户澄清：财务公司需要评估/评审业务单位的授信金额、授信期限或不授信，接收业务单位提供的材料信息及外部专业软件检索信息，开展综合风险评估和尽调。

| 要求 | 已确认内容 |
|---|---|
| C01-1 评审方 | 财务公司是开展评估/评审的一方 |
| C01-2 被评审对象 | 业务单位是提供材料、接受授信评审的对象 |
| C01-3 业务目标 | 评审授信金额、授信期限或不授信；风险分析和尽调服务于该目标 |
| C01-4 内部来源 | 业务单位提供的材料及信息 |
| C01-5 外部来源 | 外部专业软件的检索信息，是本场景正式取证来源 |
| C01-6 分析方式 | 对两类信息进行综合风险评估和尽调，不能只概述财务数据或罗列检索结果 |

被评审单位的准入范围、集团关系、实际授信政策、审批机构、当前专业软件名称与接口均未确认，不从角色名称推导这些事实。

### 1.2 已确认的来源、项目与策略边界（Q44—Q47）

## 2. 对通用引擎的影响

C04明确外部检索属于通用引擎，预算经营等场景也能配置使用。本场景只声明自身的信息需求和质量要求，不拥有专属检索模块或一套单独的检索生命周期。

### 2.1 事实来源扩展

外部专业检索是本场景需要接收的输入，与单位材料一起登记为报告依据。Q29原先“外部信息通过明确任务引入”的原则继续适用：该场景可以配置检索取证任务，但不因此放开任意联网补事实，也不表示已经授权某个付费服务或取得查询权限。

用户已确认专业信息通过HTTP/MCP服务提供。服务返回应归档并映射为同一证据契约；具体端点、工具名称、认证、权限和结果字段尚未提供。不能将“支持HTTP/MCP接入”描述成已经连通某供应商。普通导出物可沿用上传路径，但不替代该场景的服务取证设计。

企查查类来源与搜索引擎来源需要区分。搜索命中、摘要、原页面以及专业数据库记录的业务含义不同；按Q44核验可追溯原文或专业记录的主体、时点和上下文后，才将关键事实按其支持范围用于报告。无法核实时明确线索身份、待核实项与影响，不将专业软件的结论一概视为适用于本次审查。

外部取证与依据封存的顺序需要明确：拟将专业检索结果在封存前归档到本轮来源清单，再进行综合分析；封存后出现的刷新结果按Q26/Q27进入后续更新或明确重建依据，不混入正在交付的旧快照。具体任务编排仍待工程契约细化。

Q42进一步明确：必查证据不足可能是检索失败或方式问题，不阻塞分析和完整交付，正文说明取得信息的范围、限制及受影响判断，必要时请求用户补件。补件请求不意味着停下等待；必要证据仍不足则沿用待复核身份，接口失败本身不等于业务风险成立或不存在。Q43确认按场景时效复用项目归档结果，主体/查询条件/范围变化、过期或用户要求时刷新相关任务，单纯改措辞不重查。

### 2.2 主体与意见分离

项目需要区分评审方和被评审单位；额度模型、等级评估流程和报告审查也应分开。报告可核对已提供的额度、等级、期限与主体/时点/材料的一致性，不能据此改写外部流程的权威结果。

“报告正式版”沿用Q22的质量身份，不因风险报告完成就推定外部授信业务流程已经完成。实际是否把报告送入审批/业务系统尚未授权或设计，不在本轮增加自动授信动作。

### 2.3 财务计算、外部结果与风险判断

财务指标、对比与明确规则校验仍由程序执行；材料理解、风险判断和策略起草由宿主语言模型承担，关键结论独立审阅。授信额度来自授信模型，授信等级来自专门流程；期限依据等级关系确定，映射的实际维护者和接口细节还需确认。

若未提供额度/等级/期限或其依据，报告保留对应信息缺口和审查限制，不重新发明评级、授信公式或期限表。外部结果是否为正式版的必需输入由场景质量规则明确；不因此停止其余可以完成的风险分析。

授信管理制度、风险政策和审查清单仍可作为场景参考资料，用于风险审查与策略依据；这与要求报告项目实现额度模型是不同职责。

Q46明确风险报告先行与结果补充是同一项目的不同修订路径。外部结果后补时，复核其与本项目事项、主体和基准的对应关系；无法对应则保留冲突或缺口，不仅把数字贴入旧报告。结果缺失对正式身份的影响仍由场景必要证据要求判断，不能把“允许先写”理解为已经取得结果。

### 2.4 风险策略的表达与边界

按Q47，每项建议说明对应风险、依据、适用条件及待核实项，区分材料中已采取的措施和本次提出的建议。是否已落实措施需有证据，不能把建议改写为企业承诺，也不凭空指定负责人、日期或担保效果。

补件、准入/交易条件、缓释、监测及复评建议可按适用性组合；暂缓/不授信的风险建议须有政策依据，不把材料不足直接等同不授信。涉及额度、等级、期限调整时，提出提交外部流程复评的建议，不产生替代权威结果或自动执行决定。

## 4. 业务主线与接入契约

业务主线：明确授信事项、业务单位和评价时间→单位材料与通用检索取证→来源/主体/时点核对→财务指标与风险审查→核对已提供的外部授信结果或记录缺口→形成风险策略→独立审阅→完整报告交付。外部结果不是所有分析的前置条件，缺失时继续并披露；其对正式版的影响按场景规则表达。

后补路径：收到外部结果或补充原文→核对事项/主体/版本/时点及期限关系→重新评估受影响发现、策略、摘要和交付身份→验收并交付新的完整报告。与原项目不对应的新申请或新评价基准建立关联项目。

两种MCP角色需要区分：宿主通过MCP调用报告工具，与报告流程通过MCP访问专业来源，是不同的接入方向。字段及来源状态的工程建议见[外部服务与证据契约](../外部服务接入与证据契约.md)，具体连接仍待实测。

## 7. 已确认的审查专题与在建项目（Q49）

首批专题包括经营与财务、偿债与现金流、对外担保/或有事项、诉讼及外部负面事件、关联交易/资金占用、已有增信及控制措施，以及用户补充的在建项目。专题按单位业务、材料与政策判断适用性；适用但缺材料时保留缺口，明确不适用则说明依据，不能仅因没有材料就推断不存在或不适用。这不是穷尽清单或统一监管要求。

### 7.1 在建项目的业务要求与工程建议

用户已确认：存在在建项目时需要说明，并纳入综合风险审查。以下分析维度及字段为落实该要求的工程建议，具体材料清单、计算口径与政策规则仍需样例验证；不自动扩展到全部拟建项目。

| 信息/分析维度建议 | 要回答的问题及限制 |
|---|---|
| 项目身份与建设状态 | 项目名称/标识、所属单位、阶段与实际进度；保留来源、适用时点和未知项 |
| 投入及后续资金需求 | 有依据的计划总投资、已投入与后续安排，核对是否同口径；不能把计划金额当实际支出，缺口不填零 |
| 资金来源及落实情况 | 区分自筹、外部融资等已提供的安排与实际落实证据；意向/计划不写成已到位 |
| 进度及变更 | 核对已提供的进度、延期、投资变更及原因材料，无法核实时明确限制 |
| 对单位的影响 | 结合建设投入、融资安排和有依据的现金流，审查对单位资金需求、现金流和偿债能力的影响；预计收益与已实现收益分开 |
| 风险、措施与补件 | 关联风险事项、现有措施、条件性策略建议及待补材料，不据此重算授信额度或擅定等级/期限 |

在建项目是被评审单位下的业务对象，可在同一报告中有多个；报告项目仍按Q45的授信事项、单位及评价时间划分，不为每个在建项目自动另建报告工作区。同一在建项目跨表或跨材料出现时保留关联，主体或项目身份不清则待核对。

实现沿用场景专题、证据、注册算子、发现与章节依赖。场景声明项目清单及分析任务，已有计算用程序处理，影响判断与文字说明由宿主完成；不在通用引擎中增加“授信专用在建项目服务”。新项目、投资/融资/进度材料补充或更正进入影响分析，更新相关项目审查、单位现金流/偿债判断、策略及摘要；只有依赖实际成立时才联动，不把不同口径金额机械相加。

## 8. 已确认的风险程度表达（Q50）

风险程度独立于授信等级，按已确认场景/企业政策定性分级；缺规则或依据不足则待判定。业务影响、证据充分性及核验状态分别记录，不能以缺材料判低风险，不编造通用分数或授信评级映射。具体等级名称、阈值与适用政策来源仍由场景提供和验证。

## 9. 已确认的风险事项及更新（Q51）

每个风险事项保持稳定身份，记录相关主体/事项、支持及反向证据、适用时点、潜在影响、已采取措施及落实证据、建议和待核实项。同一事项跨材料关联，疑似相同但有歧义则保留待核对，不按关键词机械合并或以出现次数累计风险。

补件、更正或新证据重新评估受影响事项及引用章节，必要时更新策略、摘要和交付身份；旧事项及其原依据保留历史。事项可以关联在建项目等业务对象，但不把一个在建项目直接等同于一个风险；不同风险仍分别表达。

## 10. 真实交付样本固定结构与字体

缺材料不能删章删小节，须写缺口及影响；明确不适用须说明依据。风险章涉及加工费的固定标题来自本次标准，其适用性不能直接推广到其他行业。适用的担保、关联交易、在建项目等专题在相关固定小节内细化，不因固定目录省略Q49职责。范围、评价基准、来源与重大限制放入相关正文及结论，不额外恢复旧七章目录。

样本标题、正文和大多数拉丁字符的显式字体为仿宋。当前配置将正文、标题、数字及西文固定为仿宋，并拒绝缺字体时自动回退。字号观察：封面26磅，主要章标题15磅，第四章16磅，二级标题及正文主要14磅，表格多种字号；部分早期二级标题继承Arial西文字体。字体统一采用主要显式设置是本轮配置判断；上述差异仅作来源观察；当前采用用户明确的第10.3节统一样式，不按样本各章的偶发差异配置，也不宣称完整版式复刻。

授信模型公式、AA等级、等级期限关系、金额和人员均不由此确认为通用规则。`credit_policy`、`professional_source_provider`及`grade_term_mapping`仍保留定义缺口；真实服务、正式业务签认和真实字体的最终呈现须另行验证。

### 10.1 第一章工商信息的必需表格

用户明确“一、工商信息”使用表格呈现，包含企业名称、统一社会信用代码、法人代表、成立日期、有效期、注册资本、实收资本、注册地址、经营范围。配置采用“项目／内容”两列、字段逐行列示，表头及全部单元格为仿宋五号，即10.5磅。缺资料仍保留字段并注明未提供／待核实，注册资本和实收资本分别呈现，不替换概念或移植参考报告金额。

内容规则保存在`outline.sections.company.required_tables`，包含`subheading`、`columns`、`required_fields`及`style: compact`；字体字号统一由`scenario.presentation.table_styles.compact`定义。本轮计划不能删除或改变该规则；提交及引用展开后核对该小节中唯一的表格、两列结构、必需字段、重复字段与空值。渲染沿用共享模块，仅对该小节表格设置字体和字号；交付前读回DOCX核对中文、西文及复杂文种的字体和字号，不改变其他表格样式。完整视觉验收仍须主机具备实际仿宋字体。

### 10.2 股权结构表与股东介绍

用户进一步明确第一章“四、股权、股东及投资情况”的内容结构：先写“（一）股权结构”，以排名、股东名称、认缴资本（万元）、持股比例（%）四列逐户呈现；末行在股东名称列写“合计”，排名留空。再写“（二）股东简介、持股情况”，按股权表顺序逐户介绍有依据的股东背景、持股及控制关系。两个三级标题用独立Markdown块（`###`）保留，标题下必须有表格、正文或明确缺口。

`required_subsections`用`title`及`content`固定该二级标题下的两个三级标题、顺序和内容形式（股权结构为table、股东简介为narrative）；简介不能只有表格，须有文字或明确缺口，原始标题行与可渲染标题块须一致。`required_tables.child_heading`将股权表定位到“（一）股权结构”，`total_row`声明合计标识列、合计行留空列和需要求和的列。两个数值列在引用展开后用Decimal核对逐户之和；所有值完整可比时必须与合计一致。引用尚未展开或值明确标注未提供／待核实时，只比较可以核对的信息，不猜测总额或默认100%；有舍入或口径差异时明确披露并核实，不擅自设定容差放行。引用和来源说明放在表后，数值单元格使用数值引用或明确缺口。

示例中的股东人数、名称、出资金额、持股比例和公司简介仅为结构参考，不能作为其他报告项目的预置事实。认缴资本与实收资本分开，不能仅凭持股比例认定实际控制人；股东简介中的成立日期、业务和行业地位均须本轮证据支持。用户末句未完成的介绍不由模型补写成事实。本轮未新增股权表字号要求，沿用默认表格样式；工商信息的仿宋五号规则仍只作用于该表。
