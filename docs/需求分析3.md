# 通用长文档分析报告项目设计

## 一、核心设计原则

1. **引擎与场景分离**：引擎只管流程（解析、规划、写作、校验、组装、增量更新），场景只用配置描述（章节、指标、风险规则、模板）。新增场景只需新增一个配置包，不改代码。
2. **报告是磁盘上的结构化产物，不是对话上下文**：长报告、多轮补充、章节修改，都靠落盘的状态文件支撑。对话上下文只负责调度，不承载报告内容。
3. **确定性工作交给代码，判断性工作交给模型**：文档解析、指标计算、依赖追踪、版本管理、组装导出由脚本完成。章节写作、风险判断、结论归纳由模型完成。
4. **每轮都交付完整报告**：每次对话结束前强制执行"组装 → 校验 → 输出完整文档"，没变化的章节直接复用缓存。

## 二、整体分层

```
用户上传文档
   │
① 摄取层   解析为统一格式（md + 表格csv/json），每个片段带来源锚点（文件/页码/sheet/单元格）
   │
② 证据层   evidence store：事实、指标、表格数据，每条有 evidence_id；数值由脚本计算，不由模型心算
   │
③ 规划层   scenario 配置 → 章节规划（每章：目标、所需材料、分析问题、依赖章节）
   │         同时检查材料完整度，缺什么材料直接生成"待补充清单"
   │
④ 写作层   每章独立生成（可用子agent隔离上下文），只读取该章相关证据
   │         输出：章节正文 + 引用的 evidence_id + 关键结论 + 未解决问题
   │
⑤ 校验层   引用校验、数值一致性、章节间结论冲突、风险规则命中、完整性对照
   │
⑥ 组装层   合并章节 → 套模板 → 导出 docx/pdf/md
   │
⑦ 状态层   manifest：材料版本、章节版本、依赖图、dirty 标记、变更日志
```

## 三、场景配置包设计

每个场景是一个独立目录，引擎启动时加载：

```
scenarios/
  budget_analysis/            # 预算/经营分析
  due_diligence_risk/         # 财务公司尽调风险
  hr_compensation/            # 薪酬管理分析
    scenario.yaml             # 场景元信息、输入材料清单、输出要求
    outline.yaml              # 章节结构、依赖关系、每章写作规范
    metrics.yaml              # 指标定义与计算口径（公式、数据来源）
    risk_rules.yaml           # 风险规则/红线/阈值（尽调场景尤其重要）
    rubric.yaml               # 质量评分标准，供校验层使用
    prompts/                  # 章节级提示词模板（可选）
    templates/report.docx     # 输出模板
    glossary.md               # 行业术语与口径说明
    examples/                 # 优秀样例（few-shot，可选）
```

`outline.yaml` 示例：

```yaml
sections:
  - id: sec_overview
    title: 经营概况
    inputs_required: [财务报表, 预算执行表]
    questions:
      - 本期收入、利润、预算完成率如何？
    metrics: [revenue_yoy, budget_completion_rate]
    depends_on: []
    min_words: 800
  - id: sec_variance
    title: 预算偏差分析
    depends_on: [sec_overview]
    inputs_required: [预算执行表]
    metrics: [variance_by_dept]
  - id: sec_summary
    title: 结论与建议
    depends_on: ["*"]        # 依赖所有章节，最后生成
```

这样不同场景的差异（章节、口径、规则、模板）都在配置里，引擎代码完全通用。

## 四、多轮交付与增量更新（核心难点）

**工作区结构**（每份报告一个目录）：

```
workspace/<report_id>/
  sources/          原始上传文件（只读，带版本）
  parsed/           解析结果
  evidence/         证据库
  sections/         各章节 md + 元数据
  state/manifest.json   材料版本、章节版本、依赖图、dirty 状态、锁定状态
  state/changelog.md    每轮变更记录
  state/brief.md        全局摘要（核心结论、关键数字、术语口径），保证章节一致性
  output/               最终报告（每轮覆盖/带版本号）
```

**每轮对话先做意图路由**，分四类：

| 用户意图 | 处理 |
|---|---|
| 首次提交材料 | 全流程生成 |
| 补充材料 | 摄取新材料，对比证据库差异，找出受影响指标和章节，**只标记这些章节为 dirty**，重写后重新组装 |
| 修改指定章节 | 定位 section_id，只重写该章（可锁定其他章节），再检查依赖它的章节是否需要联动更新 |
| 调整全局参数/口径 | 影响面大，重新规划后批量标记 dirty |

**关键机制**：
- **依赖图 + dirty 传播**：材料变了 → 指标变了 → 引用该指标的章节 dirty → 依赖这些章节的汇总章节 dirty。
- **章节锁定**：用户手工确认过的章节不被自动覆盖，除非明确要求。
- **指标引用而非写死数字**：正文里的数字来自 metric_id，数据更新后能追溯到所有受影响位置。
- **每轮收尾固定动作**：`build`（组装）→ `validate`（校验）→ 返回完整报告和一份"本轮变更摘要 + 待补充问题"。

## 五、交付形态：CLI + MCP + Skills，三层叠加

不同 Agent 对 skills 的支持程度不同。**最低公约数是"CLI 命令 + AGENTS.md 说明"，MCP 和 Skills 是增强层**。建议这样分层：

1. **核心库 + CLI（Python）**：所有确定性能力做成命令，任何能执行 shell 的 Agent 都能用。
   ```
   report init --scenario hr_compensation
   report ingest ./uploads
   report plan            # 输出章节计划 + 缺失材料清单
   report status          # 各章节状态、dirty、锁定
   report evidence add/diff
   report metric compute
   report section save <id>
   report validate
   report build --format docx
   ```
2. **MCP Server**：把同样的命令暴露为 MCP 工具，适合对工具调用有结构化要求的 Agent 或 harness。
3. **Skill**：一个通用的 `long-report` skill，里面写**工作流程和意图路由规则**（什么时候调哪个命令、写章节时的约束、每轮收尾要做什么），场景配置放在 skill 的 references 里或通过 `--scenario` 加载。skill 本身要薄，逻辑下沉到 CLI。
4. **Claude Code 插件**：把 skill、章节写作 subagent、校验 subagent、斜杠命令（如 `/report-init`、`/report-revise`）、MCP 配置打包成一个插件分发。
5. **Codex / DeepSeek harness 适配**：用 `AGENTS.md`（或对应的系统提示）承载同样的工作流说明，工具走 CLI 或 MCP。具体各 harness 对 skills/插件的支持以你使用的版本为准，建议先验证再决定适配深度。

目录大致如下：

```
long-report/
  core/                  # Python 包：ingest/evidence/plan/metrics/validate/build/state
  scenarios/             # 场景配置包
  cli/                   # report 命令入口
  mcp_server/            # MCP 封装
  skills/long-report/    # SKILL.md + references
  plugin/claude-code/    # 插件打包（skills、agents、commands、mcp 配置）
  adapters/              # codex AGENTS.md、deepseek harness 提示与配置
  eval/                  # 评测集与跑批脚本
  tests/
```

## 六、长文档质量保障

长报告最常见的问题及对策：

- **上下文爆炸**：章节级生成 + 子agent隔离，每章只读相关证据和 brief.md，不读全文。
- **数字幻觉**：数值只能来自 `metric compute` 的结果，校验层扫描正文数字是否能对应到 metric 或 evidence。
- **章节间矛盾**：维护 brief.md（核心结论与关键数字），生成每章前读取，生成后更新；终稿前做一次跨章节冲突检查。
- **无依据结论**：每个关键结论要求挂 evidence_id，没有证据的结论标记为"推断"或进入"待补充问题"。
- **扫描件/复杂表格**：摄取层要单独处理 OCR 和表格还原，并保留页码锚点便于人工核对。

## 七、跨 Agent 验证方案

以**同一份评测集**在 Claude Code、Codex、DeepSeek harness 上各跑一遍，对比以下指标：

- 章节覆盖率与材料缺失识别率
- 引用准确率（抽样核对 evidence 锚点）
- 数值准确率（对照脚本计算结果）
- **增量更新正确性**：补充一份材料后，是否只重写了该重写的章节，其余章节字节级不变
- 章节修改的局部性与联动正确性
- 单次/多轮的 token 成本和耗时

评测集每个场景至少准备：1 套完整材料、1 套"缺材料"、1 个"补充材料"的第二轮、1 个"改某章"的第三轮。

## 八、落地节奏建议

1. **第一阶段（先打通闭环）**：选一个场景（建议预算经营分析，数据结构化程度高）。做摄取 → 证据库 → 章节生成 → 组装，CLI 形态，在 Claude Code 上跑通。
2. **第二阶段（多轮能力）**：manifest、依赖图、dirty 传播、章节锁定、变更日志，补充材料与改章节两条路径。
3. **第三阶段（配置化）**：把第一阶段写死的内容抽成场景配置包，再接入尽调风险和薪酬两个场景验证通用性。能不改代码就加完场景，说明抽象是对的。
4. **第四阶段（多端交付）**：MCP、Skill、插件打包，适配 Codex 和 DeepSeek harness，跑评测矩阵。
5. **第五阶段（加固）**：校验规则、权限与脱敏、评测自动化。

## 九、几个需要尽早决定的问题

- **敏感数据**：薪酬、尽调材料都很敏感，要确定数据是否允许出本地、是否需要脱敏层、工作区的访问权限怎么管。
- **最终输出格式**：docx 为主还是 pdf，有没有固定的公司模板，这决定组装层的投入。
- **材料类型**：是以 Excel/财务报表等结构化数据为主，还是以扫描 PDF、合同为主，这决定摄取层的难度。
- **人工介入点**：是否要在"章节规划"和"风险结论"处加入用户确认环节，而不是全自动。
